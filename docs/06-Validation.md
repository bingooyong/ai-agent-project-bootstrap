# 验证与验收计划

版本：V0.2；原始基线日期：2026-11-20。本文保留立项时验证矩阵和文档检查记录，其中产品 NOT_RUN 表示当时没有实现，不代表 2026-11-21 之后的执行结果。最新产品状态应结合 implementation/task-dag.json 与新增验收证据阅读，历史结果不追改为当前 PASS。

## 1. 证据分类

| 状态 | 含义 |
| --- | --- |
| PLANNED | 用例或实现已设计，尚无执行 |
| NOT_RUN | 未执行，并说明缺少实现/环境等原因 |
| STATIC_PASS / STATIC_FAIL | 已运行的结构、内容、引用或静态规则检查结果 |
| PASS / FAIL | 有命令、环境、退出码和结果记录的实际测试 |
| BLOCKED | 真实执行被明确的环境或外部条件阻断，不能写成测试通过 |

静态规则检查、单元测试、Mock 集成、真实工具加载、平台原生运行和企业 UAT 分别记录。交叉编译不等于 Windows/macOS 原生验收，第三方说明不等于本项目测试。

## 3. 样本与攻击面

目标样本包括 Go 单模块/多模块、Python 项目清单、React Vite、TypeScript 工作区、混合 Monorepo、空目录、未知语言、已有 AGENTS、自定义规则、冲突规则和不安全工程。Java Spring、Next.js、Django 等在相应探测器进入范围后增加验收，不提前纳入 MVP 完成统计。

安全夹具需包含 `.env`/私钥/证书诱饵、带执行副作用的 package 脚本、跨根和输出符号链接、`../`/盘符/UNC、大小写重复、巨大/深层 YAML、重复键/别名展开、提示注入文本、伪造计划、损坏标记与丢失 journal。诱饵使用合成数据，不读取用户真实凭证来证明防护。

文件事务需逐替换点故障注入：预检后、备份后、首个文件后、多个文件间、lock 前后及完成标记前。检查恢复不会覆盖第三方新修改，重复恢复幂等。

## 4. 运行证据格式

每次产品验证至少记录需求/用例 ID、提交与工具版本、操作系统/架构、目标夹具、执行命令与工作目录、前后摘要、时间、退出码、脱敏输出和结论。失败测试保留证据；环境失败与产品失败分别归类。

最终验收报告说明完成范围、修改文件、核心方案、执行命令、实际结果、未完事项、风险和人工决策。静态命令声明存在只能证明来源存在，不能证明测试通过。
