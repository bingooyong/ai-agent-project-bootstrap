# 背景与产品定位

**品牌：** Oh My Blueprint（OMBP）

**目标仓库：** `oh-my-blueprint`；**CLI / Go 二进制：** `ombp`

**状态：** 立项草案

**日期：** 2026-11-20

## 目标

Agent Engineering Blueprint。**One Blueprint. Every Agent.** 一套工程蓝图，统一驱动所有 AI Agent。

本项目拟建设一个本地优先的开发者工具：让 AI 编码代理进入新工程后，能够基于可验证的工程事实建立项目规则、推荐而非擅自安装工作流 Skills，并在项目演进中发现规则漂移。

Blueprint 覆盖项目画像、工程规则、Skills 能力、Agent 配置与持续治理，未来可扩展工作流和团队基线。品牌采用有记忆点的名称，命令保持四字母；不因名称扩展首期实现范围。命名状态与历史方案见[命名规范](08-Naming.md)。

产品维护可追溯的规则源，将规则按目标工具的加载语义生成或同步为适配文件，并把“规则是否仍与工程事实一致”作为持续能力。

本轮工作开始前，仓库仅含 `LICENSE` 与 `.gitignore`；本轮新增 `docs/`，尚无 CLI、规则集、Skills、模板或 CI。本文档定义的是拟议产品，不能视为已经实现的功能或已经启用的工程约束。

## 问题背景

AI 编码工具已进入日常研发，但新工程的代理配置通常仍由人工拼接：分析技术栈、写 `AGENTS.md`、复制语言与安全规范、为不同工具维护不同格式、挑选 Skills，并在构建命令、目录和框架变化后手工修订。

这种方式有四类直接后果：

| 问题 | 后果 |
| --- | --- |
| 项目事实靠猜测或复制粘贴 | 代理得到错误的构建命令、过时目录说明或不适用的规则 |
| 规则只在初始化时生成 | 工程演进后出现规则漂移，代理继续执行旧约束 |
| 多工具分别维护配置 | Codex、Claude Code、Cursor 的规则可能矛盾或丢失语义 |
| 规则、Skills 与证据未分开 | 不可信第三方指令、假测试结论或隐式生产操作可能进入日常工作流 |

用户提出的工程治理目标还包括需求、设计、实现、测试与验收之间可追溯，不能将静态检查、计划或 Mock 结果表述为真实环境验收。

## 产品定位

`ombp` 的职责边界如下。

| 属于产品职责 | 不属于产品职责 |
| --- | --- |
| 只读扫描工程，输出附证据与置信度的项目画像 | 替代 IDE、编码代理或 CI 平台 |
| 匹配版本化规则，生成可审阅的变更计划和差异 | 将 `AGENTS.md` 当作操作系统、网络或生产权限控制 |
| 适配不同工具的指令与 Skills 配置，并声明能力差异 | 自动执行任意项目脚本、自动部署或修改业务源码 |
| 检查规则引用、项目结构与受管文件的漂移 | 以静态文档检查证明测试、构建或生产验收已通过 |
| 记录规则、适配器和 Skills 的来源与锁定版本 | 未审计地下载、启用或执行第三方 Skills、MCP 与 Shell 指令 |

## 治理模型

规则分为四层，越靠近工作目录的规则越具体，但不得弱化不可覆盖的安全基线。

| 层级 | 目的 | 典型内容 |
| --- | --- | --- |
| 全局规则 | 个人或组织长期工作约定 | 证据优先、Git 安全、生产环境边界 |
| 仓库规则 | 项目的稳定事实与全局契约 | 架构、模块职责、构建测试命令、质量门槛 |
| 目录级规则 | 仅在特定模块适用的规范 | 后端事务与鉴权、前端交互、数据库迁移、测试数据 |
| Skills 工作流 | 完成专业任务的步骤与验收方法 | 初始化、需求评审、架构设计、测试、审计、验收 |

`AGENTS.md` 一类文件是对代理的行为指令，不是强制执行边界。生产访问、密钥隔离、命令许可、分支保护、发布审批和质量门禁仍须由权限系统、CI、测试与基础设施提供硬约束。

## 工程规则基线

首期规则集将把用户提出的 15 个主题收敛为可标识、可验证、可分级的规则域。规则应写成具体行为、适用条件和验证方式，而非抽象口号。

| 规则域 | 要保护的工程结果 |
| --- | --- |
| 需求理解与范围控制 | 区分明确需求、技术必要修改和自主优化；歧义记录为假设或待确认项 |
| 修改前调查 | 阅读相关实现、契约、数据模型、测试、文档和 Git 状态；保留用户未提交工作 |
| 架构一致性 | 保持模块边界，复用既有能力，防止复制实现与循环依赖 |
| 代码质量 | 正确处理异常；禁止静默失败、假实现、硬编码成功和弱化断言 |
| 数据库与数据安全 | 迁移具备兼容、回滚、重复执行、并发和数据丢失评估；禁止未授权生产写入 |
| API 与兼容性 | 修改前检查调用方；保护字段语义、事件、消息、缓存和持久化边界 |
| 安全开发 | 防密钥与敏感日志泄露，服务端鉴权，校验不可信输入与常见攻击面 |
| 测试与真实证据 | 测试与影响相称；未执行即标注未执行，失败不得隐藏，Mock 不等同真实集成验收 |
| Git 边界 | 修改前后检查状态与差异；提交、推送、历史改写、发布等按项目授权模型受控 |
| 环境与部署 | 明确 DEV、TEST、UAT、PROD；默认本地或获授权测试环境，不擅自动生产 |
| 前端交付 | 覆盖加载、空、错误、权限和重复提交状态，业务交互与视觉实现一致 |
| 文档一致性 | 评估需求、设计、API、数据库、测试、部署和变更记录是否需同步更新 |
| 依赖与第三方代码 | 先查既有能力；审查来源、许可、维护与安全风险；构建版本可复现 |
| 对抗式审查 | 从异常路径、越权、并发、数据丢失、兼容性与假实现寻找可复现问题 |
| 最终交付 | 以文件清单、实施说明、实际命令结果、未完成项、风险和人工确认项交付 |

## 产品原则

- **Local first：** 基本扫描、生成、检查和差异预览不依赖云端模型或服务。
- **证据驱动：** 技术栈、命令和模块识别都保留证据路径、置信度和待确认项；未知信息不能被补写为事实。
- **非破坏性：** 默认只读；写入遵循 Scan -> Plan -> Diff -> Apply；受管区块与用户内容分离。
- **AI optional：** 确定性扫描产生事实，模型只用于可选的解释、建议和语义审计；模型建议不直接覆盖文件。
- **适配而非复制：** 统一规则源经 Adapter 映射到目标工具；每个目标的加载、范围和不支持能力必须显式记录。
- **可复现：** 规则、Skills、Adapter 和受管文件哈希由锁文件记录，便于审计和回退。
- **安全优先：** 不读取敏感文件内容、不执行未知项目脚本、不默认联网安装外部内容。

## 分级与追溯

规则拟分为 P0 到 P3：P0 是不可由项目规则削弱的禁止性约束；P1 是必须满足的要求，企业治理阶段才引入具名、限期例外，MVP 不接受弱化；P2 是默认应遵循的工程约定；P3 是场景建议。规则定义需包含唯一 ID、来源、版本、适用范围、验证方式与覆盖策略。

每次规则变更应形成最小追溯链：需求或治理动因 -> 规则/设计决策 -> 受管生成物 -> 检查或验收证据。此链描述的是规则治理本身，不替代业务项目的需求、测试和发布证据。

## 首期边界

首期以 Go CLI 的可审阅 MVP 为目标，但本背景文档不锁定具体第三方库或版本。优先交付项目扫描、画像、基础规则解析、Codex 适配、既有文件保护、Dry Run、Diff、Check 和锁文件。

Skills Registry 的外部安装、多 Agent 完整同步、AI 语义审计、团队规则中心、Web 后台与自动部署均不属于首期实现承诺。外部工具调研及当前结论见 [07-References.md](07-References.md)。
