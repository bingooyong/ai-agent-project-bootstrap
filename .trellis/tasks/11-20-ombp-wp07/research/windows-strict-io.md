# Research: Windows strict file I/O

- Query: Can Windows implement OMBP's handle-relative, no-follow local file access and mutation contract without weakening safety, and can it be verified locally?
- Scope: mixed (workspace, installed Go and x/sys, Microsoft documentation, local runtime inventory).
- Date: 2026-11-21

## Findings

| Source | What it establishes |
| --- | --- |
| `internal/safeio/root_unix.go:129` | Each component is opened relative to a held directory, then checked for file type and device before use. |
| `internal/safeio/write_unix.go:191` | Separate create-only and digest-verified replace semantics; anchored writes, durable file flush and best-effort cleanup are part of the contract. |
| `internal/safeio/root_other.go:14` | Windows fails closed for strict project I/O today; there is no production implementation to credit. |
| `internal/updater/plan.go:236`, `internal/updater/target.go:14`, `internal/updater/transaction.go:247` and `:295` | Caller-side `EvalSymlinks` resolves the selected root before `safeio` sees it. Strict Windows root validation must happen before path resolution, and plan/recovery root binding should use the same validator. |
| `golang.org/x/sys@v0.47.0/windows/syscall_windows.go:453` and `types_windows.go:2942` | The existing dependency supplies `NtCreateFile`, `NtSetInformationFile`, `OBJECT_ATTRIBUTES`, `IO_STATUS_BLOCK` and the relevant constants. A new package is unnecessary. |
| Go 1.25.5 and 1.27.3, `src/os/root_windows.go` and `src/internal/syscall/windows/at_windows.go` | Go itself uses parent-relative native opens, but `os.Root` allows some in-root links and the Windows mutation implementation differs across versions. [GO-2026-6604](https://pkg.go.dev/vuln/GO-2026-6604) lists Windows `os.Root` mutation fixes in Go 1.26.9 and 1.27.2; the existing 1.25.5 Linux/macOS evidence does not establish Windows safety. |

Recommended sequence:

1. Define a first support window: local fixed NTFS, modern Windows versions with native test evidence. Refuse UNC, device namespace, drive-relative paths and disallowed components before opening. Open the drive root, verify `DRIVE_FIXED`, on-handle filesystem type and normalized volume identity, then walk the specified root from that handle; do not open a full path with untrusted intermediate components. Explicitly cover DOS aliases, short names, case-sensitive directories, reserved names, and alternate data streams in the Windows policy. A normalized name obtained by handle can be used as metadata for rejecting aliases; never reopen it for content. [Volume information](https://learn.microsoft.com/en-us/windows/win32/fileio/obtaining-volume-information), [Windows naming rules](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file), [normalized names by handle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew).
2. For an existing entry, open exactly one literal component with `NtCreateFile` and `OBJECT_ATTRIBUTES.RootDirectory`; for type-neutral no-follow use `FILE_OPEN_REPARSE_POINT`, omit the directory flag, then inspect on-handle attributes and file type. Refuse all reparse points, including unknown tags, before any content read, directory descent or change. Check same-volume identity and use bounded reads/enumeration on that handle. Directories used as anchors must be held throughout the operation; validate how share flags constrain rename/delete. Keep `Lstat` semantics separate from opening an allowed entry so final reparse metadata can be identified without allowing descendants. [NtCreateFile](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile), [reparse-point tags](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-point-tags).
3. For directories, validate a create-only `FILE_CREATE` + `FILE_DIRECTORY_FILE` path using proven `OBJ_DONT_REPARSE` behavior on the supported Windows versions, then verify the returned handle. Microsoft documents the object attribute separately and does not list `FILE_OPEN_REPARSE_POINT` in the compatible options for `FILE_DIRECTORY_FILE`. Treat invalid/unsupported responses as failures, with no path-based fallback. [OBJECT_ATTRIBUTES](https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_object_attributes), [NtCreateFile compatibility table](https://learn.microsoft.com/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntcreatefile).
4. For writes, use a private temporary file opened exclusively relative to the same parent and flush it. Rename by handle with `FILE_RENAME_INFORMATION` and a destination consisting of a held parent handle plus one basename. Create-only uses `ReplaceIfExists = FALSE`. Replacement needs destination identity and digest verification under the cooperative lock and a native test of target sharing behavior; an NT rename's replace flag is not compare-and-swap. Use delete disposition on the previously validated same handle for cleanup and hash-checked deletion. Windows ACL inheritance and flush/metadata durability differ from POSIX modes and directory `fsync`; report their verified guarantees separately. [FILE_RENAME_INFORMATION](https://learn.microsoft.com/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information), [FILE_DISPOSITION_INFORMATION_EX](https://learn.microsoft.com/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_file_disposition_information_ex).
5. Keep Windows fail-closed until native tests pass for readonly scans, root and child link/junction denial, same-volume constraints, alias handling, create-only collision, changed digest preservation, conditional removal and forced process crash/recovery. Audit Windows process-liveness semantics before changing journal recovery support. A cross-build only proves compilation. Initial Windows file operations should not rely on Windows `os.Root` mutation APIs while supporting the current minimum Go line.

Related contracts: `.trellis/spec/backend/ombp-go.md`, `docs/implementation/CONTRACTS.md`, WP-07 and AC-08/AC-09. Preserve the current same-root, no-follow, digest/ownership and partial-evidence rules.

## Caveats / Not Found

- This is research only. No Windows executable was run, no host was provisioned, and no filesystem or crash invariant was credited as passing.
- Bounded local inventory found QEMU binaries, no active Windows VM process, no guest in the installed UTM data directory, only a stopped Linux arm64 VM in Lima, and no `.github` workflow directory in the repository. No usable Windows runtime was identified. This does not inventory remote infrastructure or all possible manually stored guest images.
- The Windows docs do not establish atomic replacement against arbitrary concurrent writers or successful operation under every Windows filesystem and filter driver. Those remain runtime acceptance gates.
